# 项目真实缺口分析报告

## 分析范围

本报告基于以下仓库现状整理：

- `README.md`
- `AGENTS.md`
- `app.py`
- `core/` 下现有模块
- `tests/` 下现有测试
- 实际执行结果：`pytest -q`，结果为 `3 failed, 64 passed`

结论以当前代码与测试为准；当 README 描述与实现不一致时，以实现现状为主，并将文档漂移本身视为缺口。

## 当前项目已实现的核心能力

### 1. 最小 CLI 编排已经存在

`app.py` 不再只是“生成总纲”，而是已经接入了 `core/workflow_service.py`，能够串起：

1. 总纲生成
2. 章纲生成
3. 正文生成
4. 可选润色
5. 结果打印与落盘到 `data/book.json`

这说明项目已经有一个“从输入到首章正文”的最小可运行链路。

### 2. 核心 LLM 调用基础设施已经具备

项目已经实现：

- `.env` 配置加载：`config.py`
- OpenAI 兼容客户端封装：`core/llm_client.py`
- prompt 文件读取：`core/prompt_loader.py`
- JSON / 文本存储：`core/storage.py`

这些是后续继续扩展工作流的基础设施。

### 3. 关键小说生成服务已拆分成独立模块

当前已有独立服务：

- `core/outline_service.py`：生成总纲
- `core/chapter_service.py`：生成章纲
- `core/draft_service.py`：生成正文
- `core/rewrite_service.py`：润色正文
- `core/checker_service.py`：一致性检查
- `core/summarizer.py`：上一章摘要

模块边界整体清晰，符合项目“业务模块职责单一”的协作要求。

### 4. 结构化资料管理模块已经存在

当前已有：

- `core/character_service.py`：角色资料读写与去重
- `core/timeline_service.py`：时间线事件读写与校验
- `core/foreshadow_service.py`：伏笔记录与状态更新
- `core/export_service.py`：章节文本导出

这意味着项目并不是“纯文本生成器”，已经开始具备结构化创作资料管理能力。

### 5. 测试基础比表面完成度更扎实

仓库已覆盖：

- 配置与错误处理
- LLM 客户端
- prompt 加载
- 存储层
- 各主要 service
- 工作流 service
- CLI

大部分 service 都有单元测试，说明项目在“可维护性”上已经有基础，不是完全裸奔状态。

## 当前项目最明显的 10 个真实缺口

> 这里的“真实缺口”指已经直接影响项目可用性、可维护性或小说生产链路完整性的缺口，而不是泛泛的“未来可以做得更好”。

| # | 缺口 | 现状证据 | 影响 | 优先级 |
|---|---|---|---|---|
| 1 | 测试集当前不是全绿状态 | `pytest -q` 实际结果为 `3 failed, 64 passed`，失败集中在 `tests/test_app.py`，该文件仍假设 `app.py` 直接调用 `generate_outline/save_json` | 无法把“测试通过”当成真实质量基线；后续改动很难判断是否引入回归 | 高 |
| 2 | CLI / 测试 / README 已发生漂移 | README 仍强调 CLI 只覆盖总纲生成；`app.py` 实际已走 `workflow_service`；`tests/test_app.py` 仍测试旧入口 | 项目现状难以被正确理解，维护者容易在错误假设上继续开发 | 高 |
| 3 | 当前工作流只覆盖“单章首轮生成”，无法支撑连续写作 | `run_basic_workflow()` 固定 `chapter_no=1`，`previous_summary=""`，没有续写入口 | 作为“小说 agent”，最关键的连续章节生产能力还没有落地 | 高 |
| 4 | 结构化资料模块未接入主工作流 | 角色、时间线、伏笔模块都已存在，但 `workflow_service` 只从总纲里取 `protagonist` 塞给正文生成 | 已有资料管理无法反哺生成，结构化资产价值基本没有兑现 | 高 |
| 5 | 一致性检查服务存在但未进入主链路 | `checker_service.py` 有实现和测试，但 CLI / workflow 都没有调用它 | 生成结果缺少最基本的自动质检，长篇写作中角色/设定跑偏风险高 | 高 |
| 6 | 上下文承接能力未真正落地 | `summarizer.py` 存在，但没有接入章节续写流程；`previous_summary` 在工作流里始终为空字符串 | 章节之间缺少稳定衔接，越写越漂是大概率事件 | 高 |
| 7 | 产物落盘过于粗糙，缺少章节级与阶段级产物组织 | 当前主要保存到单个 `data/book.json`；`export_service.py` 未接入工作流 | 难以审阅、难以恢复、难以对单章节做局部重跑或人工修订 | 中 |
| 8 | 缺少项目级状态管理与可恢复执行 | 没有“第几章已生成章纲/正文/润色/检查”的状态模型，也没有 resume 机制 | 一旦中断或手工编辑，流程无法可靠续跑，后期编排成本会迅速上升 | 中 |
| 9 | LLM 调用工程化不足 | `LLMClient` 只有最基础的调用；没有超时、重试、请求参数控制、结构化输出约束、调用日志 | 上游模型轻微波动就可能让流程失败或返回不可控结果 | 中 |
| 10 | 结构化结果校验仍偏浅层 | 总纲、章纲、一致性检查主要只验证“是不是 JSON、字段在不在”；很少校验字段内容质量和内部一致性 | 容易把“形式上合法、内容上不可用”的结果当成成功，后续阶段才暴露问题 | 中 |

## 对这 10 个缺口的进一步说明

### 1. 测试集不全绿是最先要修的缺口

这不是“洁癖问题”，而是当前最现实的工程阻塞。

现在仓库里已经同时存在：

- 新版 CLI 测试：`tests/test_app_cli.py`
- 旧版 CLI 测试：`tests/test_app.py`

其中旧版测试直接失败，说明仓库已经出现“实现前进了，但验证基线没同步”的问题。只要这个缺口不补，之后任何缺口修复都缺少可靠回归信号。

### 2. 漂移问题不是文档瑕疵，而是认知风险

这个仓库在 README 里对项目完成度保持了克制，这点是对的；但它对 CLI 当前覆盖面的描述已经落后于代码。结果是：

- 新维护者会低估当前实现
- 也可能误判哪些能力已经串起来
- 测试作者会继续沿用旧接口假设

这会直接放大后续维护成本。

### 3. “不能持续产章”是最核心的产品缺口

项目现在更准确地说，是“能从主题生成一章样例的小说工作流骨架”，还不是“能持续写书的小说 agent”。

这不是措辞问题，而是产品边界问题。只要没有：

- 可指定章节号
- 可输入或自动生成上一章摘要
- 可读取已有结构化资料

就还不能支撑真正的章节推进。

### 4. 已有资料模块没有形成闭环

角色、时间线、伏笔模块都已经有读写和基本校验，这说明仓库作者显然打算往“结构化创作资产”方向走。

但现在这些模块和主链路基本脱节，导致：

- 维护这些资料的收益不高
- 生成与资料可能分叉
- 项目复杂度已经增加，但收益还没兑现

### 5. 检查能力存在但没有在真正需要时被调用

`checker_service.py` 的存在说明项目已经意识到一致性问题，但工作流没有在生成后自动检查，也没有把检查结果纳入产物。

这会让“检查”停留在工具层，而不是流程层。

### 6. 长篇上下文问题目前只是“有模块，没能力”

`summarizer.py` 只是一个可调用工具，还不是续写机制的一部分。对于小说 agent 来说，这种差别非常大：

- 有摘要模块，不等于有续写能力
- 有续写入口，不等于有稳定上下文策略

当前状态还停留在第一层。

### 7. 数据落盘方式还不够支持创作流程

把整个结果塞进 `data/book.json` 适合 smoke 阶段，但不适合继续迭代章节：

- 不利于人工编辑
- 不利于比较不同章节版本
- 不利于按阶段重跑

这已经开始影响可操作性。

### 8. 缺少状态模型，会阻碍后续编排扩展

一旦后面接入：

- 章节规划
- 正文重写
- 一致性检查
- 伏笔回收

就会立刻需要状态与阶段管理。现在没有这一层，说明工作流还停留在“一次性函数调用”的阶段。

### 9. LLM 调用还缺少面向真实使用的韧性

当前 `LLMClient` 的定位更像“最小封装”，而不是“可支撑工作流的可靠客户端”。

对于小说生成项目，这会导致两类问题：

1. 上游偶发错误会直接打断流程
2. 返回内容轻微偏格式，就会在后续解析阶段失败

### 10. 校验规则还不能过滤“看起来像成功”的坏结果

例如：

- 总纲字段齐全，但 `volume_plan` 内容为空或结构很弱
- 章纲有 `beats` 列表，但每个 beat 缺少关键字段
- 一致性检查返回空列表，但并不说明真的经过有效检查

目前这类结果仍可能被当成成功产物继续往下传。

## 推荐下一步顺序

推荐按下面顺序推进，优先修“能恢复工程可信度”和“能形成真实小说流程闭环”的缺口。

### 第一步：恢复可信基线

1. 先修正 CLI 相关测试漂移，确保 `pytest -q` 全绿
2. 同步整理 README 对当前主流程覆盖面的描述

原因：

- 不先修这一步，后面每次改动都没有可靠回归信号
- 文档和测试同时漂移，会持续制造误判

### 第二步：把“单章样例链路”升级为“连续章节链路”

3. 给工作流补上章节号、上一章摘要、续写入口
4. 把 `summarizer.py` 正式接入章节推进逻辑

原因：

- 这是项目从 demo 走向真正小说 agent 的关键分水岭

### 第三步：把结构化资料真正接进主流程

5. 让角色、时间线、伏笔参与章纲生成 / 正文生成 / 检查
6. 明确每一阶段写回哪些结构化数据

原因：

- 现有模块已经存在，优先把存量资产变成真实能力，比继续新建模块更划算

### 第四步：补上流程质检与可恢复性

7. 在工作流里接入一致性检查，并把结果落盘
8. 引入章节级产物组织和状态管理

原因：

- 没有这一步，流程仍然难以长时间运行和反复迭代

### 第五步：最后再补工程韧性

9. 为 LLM 调用补上重试、超时、日志、参数控制
10. 强化结构化结果校验

原因：

- 这是重要缺口，但应该建立在主工作流边界已经稳定之后

## 综合判断

当前项目不是“完成度很高、只差优化”的状态，也不是“只有零散脚本”的状态。

更准确的判断是：

> 它已经具备小说 agent 的基础骨架和最小首章链路，但距离“可持续产出多章节、可检查、可恢复、可维护”的真实工作流还有一段明显距离。

如果只允许优先修一个问题，最值得先修的是：

**测试基线失真（`pytest -q` 当前失败）**

如果只允许优先补一条能力链路，最值得先补的是：

**把当前单章工作流升级为可连续推进的章节工作流，并接入已有摘要/结构化资料模块。**
